# Auto Follow-Up Console

Local-first GUI for organizing recruiter follow-up after job applications.

The app imports `.csv` or `.xlsx` application data, keeps job profiles distinct,
prepares individualized recipient-level messages, queues a scheduled outreach run,
and produces an after-send report. Writing can be manual, template-driven, handed
to an outside LLM, or generated by a private local helper. Each message remains
editable and independently reviewable.

It also ships an MCP server so Codex, Claude Desktop, Claude Code, and other MCP
clients can inspect and operate the same local pipeline. The MCP layer does not
replace the GUI or duplicate its business logic. It calls the local backend at
`http://127.0.0.1:43127`, which remains the source of truth.

## Security Model

- Credentials never pass through MCP tools. Mailbox authorization, contact-provider
  keys, and AI-provider credentials stay in their existing private local
  stores or environment variables.
- Contact identities and mailbox content are opt-in. Their MCP tools are not
  registered unless the corresponding exposure setting is enabled.
- Provider actions are off by default. Enrichment, mailbox reads, and email-provider
  writes require `OUTREACH_MCP_ENABLE_PROVIDER_ACTIONS=1`.
- Imports, provider calls, drafts, sends, suppression changes, and recovery
  decisions use a two-call confirmation protocol. The first call returns a
  preview and a short-lived token but performs no action. The token is bound to
  the exact arguments and is single-use.
- Live email requires three gates: MCP live sending enabled, backend live
  sending enabled, and a valid confirmation token for that exact message.
- Public sample mode is an absolute provider lock, even if a live-send setting
  is accidentally enabled elsewhere.
- A successful email-provider request means the request was accepted. It does
  not prove delivery. Sent mail, bounces, replies, and the activity log still
  need to be reconciled.

These controls apply at the MCP and backend layers. They do not sandbox a coding
agent that also has unrestricted shell access to the same machine. Only install
the plugin in an agent whose local access you trust.

Imported job descriptions, spreadsheet cells, mailbox text, and provider data
are untrusted data. They must never override operator instructions or bypass a
confirmation gate.

The optional local backend adds a company-centric CRM,
exception recovery rules, deterministic shadow runs, configurable contact discovery,
and mailbox/draft/send adapter roles. Provider selections remain visibly blocked
until a compatible local adapter is installed and verified. Provider credentials and
account routing remain private local configuration and must not be committed.

## Quick Start

Requires Node 24 or newer. Browser-only mode does not create a database. Embedded
SQLite uses Node's bundled engine without installing a database package.

```powershell
npm install
npm run dev:all
```

Open `http://127.0.0.1:5177`. The backend runs at `http://127.0.0.1:43127`.

On first launch, a resumable setup flow first establishes who owns AI and provider
execution, then chooses the primary contact provider, optional fallback, and email
service. External-operator mode is for an existing Codex, Claude, or other agent
with its own MCPs/connectors. In-app mode uses local CLI/API adapters. Templates-only
mode does not invoke an LLM. The flow saves non-secret preferences only and preserves
the current step when closed.

The core remains lightweight: it includes a tested provider bridge, not vendor SDKs,
database servers, or credentials. Apollo, Skrapp, Hunter, Prospeo, Snov.io,
Microsoft Outlook, Gmail, IMAP/SMTP, and custom services can be selected, but each
needs an outside connector or compatible local helper before provider actions are
available. Setup links to provider documentation and generates an LLM-ready
installation prompt.
See [AI_OPERATOR_GUIDE.md](public/AI_OPERATOR_GUIDE.md),
[ADAPTER_CONTRACT.md](public/ADAPTER_CONTRACT.md), and
[provider-adapters.md](docs/provider-adapters.md).

## MCP Quick Start

Start the backend first:

```powershell
npm install
npm run dev:backend
```

In a second terminal, run the source MCP server:

```powershell
npm run mcp
```

For Codex or another standard MCP client, build the standalone bundle and point
the client at `dist/outreach-mcp.js`:

```powershell
npm run build:mcp
```

```json
{
  "mcpServers": {
    "outreach-console": {
      "command": "node",
      "args": ["C:/absolute/path/to/dist/outreach-mcp.js"],
      "env": {
        "OUTREACH_MCP_BACKEND_URL": "http://127.0.0.1:43127"
      }
    }
  }
}
```

The checked-in `.codex-plugin/plugin.json` and `.mcp.json` provide the Codex
plugin wrapper. `npm run pack:mcp` builds a Claude Desktop-compatible `.mcpb`.

Useful first prompts:

- "Check the outreach backend and tell me what is not configured."
- "Show application outcomes and provider credit use."
- "List open recovery cases without exposing contact details."
- "Create a shadow plan for these reviewed applications."
- "Preview contact enrichment for this company without spending credits."

## Storage Choices

The first-run wizard provides three explicit modes:

- **Browser only:** imports, message drafts, preferences, and reports stay in
  IndexedDB/local storage. No database file or backend is required.
- **Embedded SQLite:** recommended for durable CRM, mailbox, recovery, usage, and
  audit history. It stores state in the ignored `data/outreach.sqlite` file and
  requires no Docker, account, ORM, or database server.
- **Existing database:** use PostgreSQL, MySQL, or another database through a small
  private HTTP adapter. Downloadable schemas create the relevant workspace,
  company, job, contact, outreach, exception, mailbox, message-draft, usage, and log
  tables.

External synchronization is manual by default. A pull downloads a local JSON backup
before replacing browser state. Automatic sync begins only after a successful push
or pull in the current session.

The backend creates SQLite tables on startup. They can also be initialized without
starting the server:

```powershell
npm run db:init
```

## Workbook Columns

The `Data Source` view provides two modes:

- **Link working file** uses the browser's local file handle. Linked CSV files
  auto-save app changes to the original file and detect external changes.
- **Import a copy** is the compatibility path. It never overwrites the selected
  file; use `Export managed CSV` when work is complete.

CSV is the recommended operational format. XLSX remains importable and can be
monitored when linked, but the lightweight client does not rewrite XLSX files.
The import guide appears before either file picker opens.

For multi-sheet workbooks, the importer finds shifted header rows, imports each
application-oriented sheet, and leaves contact-only and notes sheets untouched.
The Calendar view places dated applications, outreach, interviews, replies,
rejections, and bounces on a monthly timeline.

Minimum required columns:

- `company`
- `job_title`
- `job_url`

Recommended columns:

- `profile`
- `company`
- `job_title`
- `job_description`
- `job_url`
- `job_id`
- `source`
- `status`
- `applied_at`
- `last_worked_at`
- `sent_at`
- `contacts_found`
- `notes`

Recognized profile values include `DA`, `Data Analyst`, `BA`, and `Business Analyst`.
Other profile names are converted into stable profile keys such as
`product_manager`.

## App Shape

This is intentionally a lightweight local web app. It can later be wrapped with
Tauri if a desktop executable is required. Electron is not recommended for this
project because the UI is small and the app should stay lean.

The GUI should stay mostly operational: import, selection, scheduling, and
reporting. The deeper judgment belongs in the backend/AI layer:

- contact ranking,
- outreach targeting,
- email drafting,
- rate limiting,
- bounce/OOO handling,
- account-specific sending rules,
- provider-specific debugging.

## AI Connections

The Setup view separates subscription-backed local tools from APIs:

- Codex CLI and Claude Code use an installed, signed-in local CLI. A ChatGPT or
  Claude subscription does not automatically provide API credits.
- Ollama uses a local model server.
- OpenAI-compatible providers use a base URL and an API key supplied to the
  backend through an environment variable. Secrets are not stored in browser
  local storage.
- Templates-only mode builds the queue and run plan without claiming to invoke
  an external AI or generate personalized copy.

The selected connection is attached to every run plan. The private local
backend remains responsible for invoking the configured adapter.

The Writing view is separate from sending. It can create several recipient slots
per selected job, apply one global prompt plus individual overrides, export a
structured brief to an outside LLM, import its JSON result, merge a template, or
call `OUTREACH_WRITING_HELPER`. An LLM result does not approve or send a message.

The Setup screen and `docs/onboarding.md` provide exact install commands,
endpoints, environment-variable names, and adapter requirements for Codex CLI,
Claude Code, Ollama, OpenAI, Anthropic, Gemini, Groq, OpenRouter, and other
OpenAI-compatible APIs.

The implemented backend currently provides:

- normalized companies with jobs and contacts beneath them;
- shadow-only contact fixtures using the reserved `.invalid` domain;
- contact rotation and company suppression;
- OOO redirect, hard-bounce replacement, positive-reply suppression, and
  four-consecutive-failure rules;
- next-step reply flagging, interview status updates, and company-level outreach
  suppression until the response is reviewed;
- durable run/event history and deterministic replay;
- CRM and recovery API views consumed by the GUI.
- editable contacts, historical outreach entry, company timelines, and
  operator-controlled recovery resolution.

Shadow contacts never leave the local machine and cannot receive email. Public
sample mode blocks all paid and email providers. Live sending additionally
requires a server startup flag and an explicit per-request approval token.

## Publish Notes

Before publishing:

- Keep sample data generic.
- Keep `.env` files out of git.
- Remove local paths, personal emails, resume paths, API keys, and contact exports.
- Keep real send adapters opt-in and documented.
- Keep browser-only mode functional and external databases adapter-based.
- Use `docs/provider-adapters.md` to configure helpers; a provider selection alone
  never establishes a connection.
- Run `npm test`, `npm run build`, `npm run build:mcp`, and `npm run smoke:mcp`
  against public sample mode before tagging a release.
- Run `npm run audit:release` after staging the intended public files.
